# 修改日志：修复「SRT 后端下发码率 / fps 不起作用」

- 日期：2026-06-28
- 链路：SRT（独立链路，方案 A：iOS → SRS srt_server → 桥接 WebRTC）
- 影响文件：`srs/Managers/WebRTCManager.swift`
- 影响范围：仅 SRT 模式；SRS / P2P 不受影响（逻辑分支隔离），PC / 网页端零改动
- 关联历史：`949acc2`（SRT 切档分辨率回归修复，本次 bug 即由该提交引入的同步写法导致）

---

## 一、问题现象

SRT 推流时，后端通过控制指令动态下发「码率（bitrate）」「帧率（fps）」，
SRT 链路不响应——码率不变、编码器帧率参数不变。
同样的后端指令在 **SRS / P2P 链路均正常生效**。

## 二、根因分析

后端控制指令统一进入 `WebRTCManager.applyThinRemoteConfig(_:)`：

- `ptype == "bitrate"` → `setQualityPercentage` → `applyEffectiveBitrateToWebRTC` → `setBitrateRangeKbps`，
  更新 `targetBitrateKbps`，并对 SRS（`videoSender`）/ P2P（`applyBitrateToAllSessions`）**即时下发**。
- `ptype == "fps"` → `setAverageOutputFPS`，更新 `frameThrottler.targetSendFps`，
  对 SRS（`videoSender.maxFramerate`）/ P2P（`applyFramerateToAllSessions`）**即时下发**。

SRT 链路原本只在「每秒 onSample 统计回调」里同步一次编码参数，且写法有两处缺陷：

### 缺陷 1（码率不生效 / 核心）：变更检测被预写自废

`SRTManager.setEncodeParams(width:height:fps:bitrateKbps:)` 内部用「变更检测」决定是否下发到
HaishinKit 编码器：

```swift
let changed = width != encWidth || height != encHeight
    || fps != encFps || bitrateKbps != targetBitrateKbps
...
guard changed, isPublishing else { return }   // 无变化则不下发
```

而 onSample（以及 startSRTPublish 初始注入）在调用 `setEncodeParams` **之前**先执行了：

```swift
self.srtManager.targetBitrateKbps = self.targetBitrateKbps   // ⛔ 预写
self.srtManager.setEncodeParams(..., bitrateKbps: self.targetBitrateKbps)
```

预写后，`bitrateKbps != targetBitrateKbps` **恒为 false** → `changed` 恒为 false →
`setEncodeParams` 直接 return，**新码率永远到不了编码器**。这就是「后端下发码率不起作用」的根因。

### 缺陷 2（fps 编码器参数不生效）：用了采集 fps 而非推送 fps

onSample 同步时 fps 取的是 `getCaptureResolutionForProfile(currentProfile).fps`
（即档位**采集**帧率，每档固定），而不是后端下发并落地的**推送**帧率
`frameThrottler.targetSendFps`。因此：

- 编码器 `expectedFrameRate` 永远停在采集帧率，后端调 fps 对编码器参数无感；
- 且该值每档恒定，`fps != encFps` 也永远为 false，进一步让 `changed` 判不出变化。

（注：SRT 实际喂帧速率由 `frameThrottler` 节流，后端 fps 仍会改变「实际帧数」；
但编码器 `expectedFrameRate` 与实际帧率长期不一致会影响码控，且与 SRS/P2P 行为不一致。）

> 为什么「切档/分辨率」却正常：切档会改变 width/height，`changed` 能判出变化，故只有
> 「纯码率 / 纯 fps」变更被吞掉，正好对应用户观察到的现象。

## 三、修改内容

新增统一同步入口 `WebRTCManager.syncSRTEncodeParamsFromCurrentState()`，并在与 SRS/P2P
完全对齐的位置即时调用：

1. 新增私有方法 `syncSRTEncodeParamsFromCurrentState()`
   - 仅 `currentConnMode == .srt && srtManager.isPublishing` 时生效，其余为零开销空操作；
   - 分辨率取当前档位、**fps 取 `frameThrottler.targetSendFps`（推送目标）**、码率取 `targetBitrateKbps`；
   - **不预写** `srtManager.targetBitrateKbps`，交由 `setEncodeParams` 自行比对，恢复变更检测。

2. `applyEffectiveBitrateToWebRTC()` 末尾
   - 在已有 `if currentConnMode == .p2p {...}` 后新增 `if currentConnMode == .srt { syncSRTEncodeParamsFromCurrentState() }`，
     使后端调码率对 SRT **即时生效**（与 SRS/P2P 同步时机一致）。

3. `setAverageOutputFPS(_:)` 末尾
   - 调用 `syncSRTEncodeParamsFromCurrentState()`，使后端调 fps 对 SRT 编码器 `expectedFrameRate` **即时同步**。

4. `startSRTPublish` 初始注入
   - 删除自废的 `srtManager.targetBitrateKbps = targetBitrateKbps` 预写；
   - 初始 fps 改用 `frameThrottler?.targetSendFps ?? initRes.fps`（推送目标，回退采集 fps）。

5. `startSRTPublish` 内 `onSample` 周期回调
   - 由「预写 + 采集 fps」的旧写法改为调用 `syncSRTEncodeParamsFromCurrentState()`，
     作为切档 / 漏发的**周期性兜底安全网**（无变化时为空操作，不会每秒重配编码器）。

## 四、为什么安全 / 与 SRS·P2P 对齐

- 同步时机与 SRS/P2P 一致：码率走 `applyEffectiveBitrateToWebRTC`、fps 走 `setAverageOutputFPS`，即时下发。
- 仍保留 onSample 每秒兜底，避免任何边缘漏发；得益于恢复后的变更检测，稳态下不会每秒重配编码器。
- 分辨率红线不变：fps 自适应只改 `bitRate / expectedFrameRate`，`videoSize` 仅随档位变化
  （见 `SRTManager.applyVideoSettingsToStream` 注释），不触碰 P2P 历史回归点。
- 解耦红线不变：未新增对 SRSManager / P2PManager 的引用；删除新增方法与 3 处调用即可回退。

## 五、验证建议（真机）

1. SRT 推流稳定后，从后端依次下发：码率 30% → 80% → 30%，观察 PC 顶栏码率与画质随档变化。
2. 下发 fps（如 60→120→240，落地 /4），观察 PC 端实际帧率随之变化、且不影响分辨率。
3. 切档（low↔high↔ultra）后再调码率/fps，确认仍即时生效（兜底安全网正常）。
4. 对照 SRS / P2P 同操作，确认三链路行为一致。

## 六、回退方式

还原 `srs/Managers/WebRTCManager.swift` 本次改动（删除 `syncSRTEncodeParamsFromCurrentState()`
及其 4 处调用，恢复原 onSample / 初始注入写法）即可，无其它文件牵连。
